## 落地路径

登录拿 cookie → 遍历课程列表 → 每门课拉章节树拿到所有 `leafID`（作业、考试都在叶子节点上）→ 逐个查 `leaf_info` 取标题/发布/截止/完成状态 → 把数据映射成待办（标题、开始时间、截止时间、课程名、状态、原链接）→ 按 `leafID` 去重做增量同步 → 输出目标。

## 需要注意的坑（按实际影响排序）

1. **公告是唯一的不确定项**。作业链路我很有把握，公告我没能确认到一个稳定的公开端点，它是通知中心/课程详情页里的内容。但它对你的目标来说不那么关键——待办基本都来自作业和考试，公告多数是通知性质。真要抓，登录后在浏览器 F12 里对通知中心筛 XHR 就能定位到，属于"验证一下就清楚"的问题。
2. **登录态会过期**，cookie 失效后要重新扫码。所以程序必须能识别 401/跳登录页并提示你重新授权，不能默默失败。
3. **接口无契约保证**，雨课堂前端一改版就可能挂，需要留好"字段缺失时不崩、只跳过"的容错。
4. **时间字段的边界情况**：时区（服务器给的可能是时间戳或字符串）、无截止时间的作业、教师延期后截止时间变化——延期这点其实是个优势，重新同步会自动更新待办。
5. **去重与增量**：必须用稳定 ID（`leafID`/`exam_id`）而不是标题，否则改个标题就会产生重复待办。
6. **请求频率**：单账号串行 + 加延迟，别并发轰，学生账号被风控得不偿失。
7. **合规**：这是非官方抓取、且用的是你自己的账号数据。自用没问题，但不要做成给别人用、更不要收集他人 cookie。这在技术上也会让账号风险明显上升。

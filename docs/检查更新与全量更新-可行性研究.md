# 检查更新 → 直接下载并全量更新：可行性研究

> 研究时间：2026-10-12 · 对象：`D:\Project\HomeworkReminder`（.NET 10 / Avalonia 桌面端）
> 结论：**可行，而且比预期简单得多。** 本文含实测数据与落地方案。

---

## 0. 结论先行

| 问题 | 答案 |
|---|---|
| 能从 Gitea/GitHub 下载程序吗？ | ✅ **可以**，两个源都已有现成 asset |
| 能直接全量更新吗？ | ✅ **可以**，且更新就是**替换一个 exe 文件** |
| 用户数据会丢吗？ | ❌ **不会**，数据在 `%LOCALAPPDATA%`，与程序目录分离 |
| 登录态会丢吗？ | ❌ **不会**，WebView2 缓存在 exe **旁边**、不在 zip 里 |
| 唯一的技术门槛 | ⚠️ **运行中的 exe 不能覆盖/删除**，必须先让父进程退出 |
| 现在的实现到哪一步了 | 只到「检查 + 提示去 release 页看」，**没有下载** |

## 1. 实测数据（全部为本轮真实抓取，不是推测）

### 1.1 两个源的 release asset 都现成

| 源 | latest tag | Windows 资产 | 大小 |
|---|---|---|---|
| Gitea（`origin`） | `v1.3.1` | `HomeworkReminder-v1.3.1-win-x64.zip` | 17.2 MB |
| GitHub（`main`） | `v1.3.1` | `HomeworkReminder-v1.3.1-win-x64.zip` | 17.2 MB |

另有 `HomeworkReminder-v1.3.1-android.apk`（45.5 MB）。历史 6 个 release 命名规律一致。

- Gitea：`https://git.pigeon-lin.top/lin/ChangjiangYu_HomeworkReminder/releases/download/{tag}/{asset}`
- GitHub：`https://github.com/linpigeon/ChangjiangYu_HomeworkReminder/releases/download/{tag}/{asset}`

### 1.2 ★ zip 里**只有一个 exe**（这是方案简单的根本原因）

```
条目总数: 1
  HomeworkReminder.Desktop.exe    未压缩 41.5 MB
```

**没有** `.WebView2`、**没有** pdb、**没有** dll、**没有**用户数据。

**且与发布目录的 exe 完全一致**（SHA256 逐字节相同）：

```
发布目录 exe           2187F424E6F3F308E01E18BA53B689AAB045A3C56FBCC728B818997D37E64B1A
zip 内 exe             2187F424E6F3F308E01E18BA53B689AAB045A3C56FBCC728B818997D37E64B1A
zip 自身               1C878B32529D562E0CFA5744D654378A7F68F87228451EB75DCF0055A55003F2
```

> 41.5 MB → 17.2 MB 是 zip 压缩率，属正常。

### 1.3 ★ WebView2 缓存在 exe **旁边**，不在 exe 内部

发布目录实测内容：

```
DIR   HomeworkReminder.Desktop.exe.WebView2     ← 运行时自动创建，约 67 MB
FILE  HomeworkReminder.Desktop.exe
FILE  HomeworkReminder.Desktop.exe - 快捷方式.lnk
```

**所以只替换 exe 不会碰它** → **登录态天然保留，不需要任何额外处理**。

### 1.4 ★ 运行中的 exe：能改名，但不能覆盖/删除（**唯一门槛**）

exe 正在运行时实测：

| 操作 | 结果 |
|---|---|
| **重命名** | ✅ **成功** |
| 覆盖写入 | ❌ 失败 |
| `File.Move(src, exe, overwrite: true)` | ❌ 失败 |
| 删除 | ❌ 失败 |
| **进程退出后再替换** | ✅ **成功** |

这是 Windows 的既定语义：**打开中的文件不能删除或覆盖，但可以改名**
（`FILE_SHARE_DELETE` 允许 rename，不允许 delete/overwrite）。

> **这条决定了更新架构**：更新器必须在**父进程退出后**才替换文件，并且**要重试**。

### 1.5 用户数据位置（更新安全的前提）

`AppPaths.DataDirectory` = `%LOCALAPPDATA%\HomeworkReminder`
（可用 `HOMEWORKREMINDER_DATA_DIR` 覆盖，不可写时回落临时目录）。

待办缓存、会话、设置**全部在这里**，与程序目录完全分离 → **全量替换 exe 不影响任何用户数据**。

## 2. 落地方案

### 2.1 总体流程

```
① 发现新版本（已有：并行查 GitHub + Gitea，比版本号）
② 用户点「下载并更新」
③ 下载 zip 到 %TEMP%\HomeworkReminder\update\
④ 校验 SHA256 + 解出 exe
⑤ 释放更新器脚本（嵌入资源，写进临时目录）
⑥ 启动更新器，同时传：新 exe 路径 / 目标 exe 路径 / 当前 PID / 是否重启
⑦ 主程序自行退出（更新器已在等）
⑧ 更新器：等父进程退出 → 替换 exe（带重试）→ 校验 → 重启 → 清理自身
```

**关键点**：更新器是**独立进程**，它不持有目标 exe 的句柄，
而主程序退出后那个锁就没了，所以替换必然成功。

### 2.2 更新器：用嵌入的 PowerShell 脚本（推荐）

| 方案 | 评价 |
|---|---|
| **嵌入 PowerShell 脚本**（推荐） | 零额外产物、逻辑可读可测、`-File` 传参 + `ProcessStartInfo.ArgumentList` 自动处理引号与特殊字符 |
| 批处理 `.cmd` | ❌ 路径含 `&`/`^`/`(`/空格时**极易被破坏**，不要用 |
| 单独的小 updater exe | 最稳（自带 .NET，不依赖系统 PowerShell 版本），但要多维护一个项目与发布产物 |

> **必须用 `ProcessStartInfo.ArgumentList`（数组）而不是拼 Arguments 字符串**，
> 否则路径里有空格或引号就会拼错。
> 另外 **不要走 `cmd /c`**——那会再引入一层引号解析。

**更新器要处理的情况**（都是实测/常识会遇到的）：

```powershell
# 1. 等父进程退出（带超时，避免父进程卡住时无限等）
# 2. 替换：先尝试直接 Move(overwrite)；失败则重试若干次（间隔 0.5s）
#    重试仍失败 → 退化为「旧文件改名 .old，再放下新文件」
#    （改名在文件仍被占用时是允许的 —— 见 §1.4 实测）
# 3. 校验替换后的 exe 的 SHA256 与预期一致（防止替换出半截文件）
# 4. 重启新 exe（继承原来的命令行参数）
# 5. 清理：临时 zip、解压目录、.old 残留、以及脚本自身
```

**为什么第 2 步要「改名兜底」**：杀毒软件/索引器可能短暂持有句柄，
`File.Move` 会偶发失败。改名路径能绕过「文件被占用不能覆盖」这条限制。

### 2.3 资产定位：不要硬编码文件名（**重要**）

当前命名是 `HomeworkReminder-{tag}-win-x64.zip`，但这是**人工上传时定的**，
没有任何代码约束它。建议按优先级：

```
1. 若 release 里有 manifest 资产（如 update-manifest.json）→ 读它拿 URL + SHA256
2. 否则按模式在 assets 里找：名称同时含 "win-x64" 和 ".zip"（不区分大小写）
3. 都找不到 → 明确报错「未找到适用于本平台的更新包」，不要猜
```

**建议增加 manifest**（一个几行的 JSON），好处是**把更新与资产命名解耦**：

```json
{
  "version": "1.3.2",
  "file": "HomeworkReminder-v1.3.2-win-x64.zip",
  "sha256": "…",
  "size": 18000000
}
```

有了它，以后改命名、加镜像、换 CDN 都不需要改客户端。

### 2.4 完整性校验（必须做）

下载 17 MB 的东西走公网，**必须校验**。三级：

| 级别 | 手段 | 说明 |
|---|---|---|
| **必须** | **SHA256** | 从 manifest 或 API 拿预期值；**HTTP 头里没有 SHA，别指望它** |
| 建议 | 解出的 exe 的**文件版本** | 与 tag 比对（`FileVersionInfo`），做二次确认 |
| 可选 | Authenticode 签名 | 目前**未签名**，加了签名后可用 `Get-AuthenticodeSignature` 强校验 |

> 若暂时没有 manifest，退而求其次：**校验解出 exe 的版本 ≥ 远端 tag**
> ——这能拦住"下载到旧包/错包"，但拦不住被篡改。

### 2.5 发布侧要改的（**不改的话更新会循环**）

**现状**：版本号**只在 `HomeworkReminder.csproj` 手工写**（当前 `<Version>1.3.1</Version>`），
而 release tag 是**另外手工打**的。

**风险**：若 tag 是 `v1.3.2` 但 csproj 忘了改，就变成
「检查更新说 1.3.2 更新 → 更新完程序仍报 1.3.1 → 下次检查又说要更新」——**无限更新循环**。

**建议**：给发布流程加一步，**从 tag 自动写入版本号**，或至少在打包脚本里校验
`csproj 的 Version == tag`，不一致就拒绝出包。

另外目前**没有 release 自动化**（没有 `.github/workflows`，也没有打 tag + 传资产的脚本）：
> 建议补一个 `tools/release.ps1`：读 tag → 校验版本一致 → `publish.ps1` → 压缩 → 生成 manifest → 上传到两个源。

## 4. 风险与注意

| 风险 | 说明 | 缓解 |
|---|---|---|
| **更新循环** | tag 与 csproj 版本不一致（见 §2.5） | 发布侧强校验 |
| **运行方式误判** | 若在开发态用 `dotnet run` 触发更新，`Environment.ProcessPath` 指向 **dotnet 宿主**，替换它会**破坏开发环境** | 更新前判断 exe 路径不以 `dotnet` 结尾、且确实是本应用；开发态直接**拒绝**自动更新 |
| **安装目录不可写** | 若装在 `Program Files`，替换 exe 会失败 | 明确报错并引导手动下载；或坚持"解压即用"的分发方式（当前就是） |
| **杀软/SmartScreen 拦新 exe** | 未签名的 exe 被替换后首次运行可能被拦 | 长期做代码签名；短期提示用户 |
| **PowerShell 版本** | Windows PowerShell 5.1 与 PowerShell 7 行为略有差异 | 脚本只用最基础语法；或改用独立小 exe 彻底规避 |
| **下载中断** | 17 MB 在弱网下可能失败 | 重试 + 清理半截文件；不要续传到同一个路径 |
| **`.WebView2` 意外被删** | 若更新逻辑顺手清理目录会误删登录态 | **更新只允许动 exe 这一个文件**，其他一律不碰 |
| **`--selfcheck` 等自检被更新打断** | 自检进程若触发更新会替换自己 | 更新入口只在设置页 UI 暴露，不进自检路径 |

### 4.1 必须遵守的一条铁律

> **更新过程只允许修改一个文件：目标 exe。**
> 不删目录、不动 `.WebView2`、不碰 `%LOCALAPPDATA%`。
>
> 这条同时保证了登录态与用户数据安全，也让回滚变简单（旧 exe 改名保留即可）。

## 5. 建议实施顺序

```
1. 发布侧先补齐：版本号与 tag 同步 + 生成 manifest（否则客户端做完也没法可靠验证）
2. UpdateService 扩展：完整 release 查询 + 资产定位 + 下载（先只做「下载到临时目录」，
   不做替换，可单独验证下载与校验）
3. 加 --checkupdate 自检：覆盖版本比较、资产挑选、SHA256 校验
4. 更新器脚本 + UpdateApplier：在**临时目录里用一个副本 exe 演练**替换流程，
   确认不动真实安装目录
5. 接 UI：设置页「下载并更新」+ 进度文案
6. 端到端演练：发布一个 v1.3.2 的测试 release（可先发 prerelease），
   从 v1.3.1 走一遍完整更新
```

**第 4 步的演练方式很关键**：把发布版 exe 拷到临时目录、在临时目录里跑替换流程，
**不要直接拿 `publish\` 或用户实际安装的目录做实验**。

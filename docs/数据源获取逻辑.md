## 一、总览：三条链路、四条数据通道

三个来源的**数据形态与获取方式差异很大**，因此各自独立，但产出的模型是统一的。

```
                        ┌─────────────────────────────────────────────┐
                        │            同步编排（MainViewModel）          │
                        └─────────────────────────────────────────────┘
                                          │
        ┌─────────────────────────────────┼─────────────────────────────────┐
        │                                 │                                 │
   ┌────▼─────┐                     ┌─────▼──────┐                    ┌─────▼─────┐
```

### 关键取舍：为什么学习通是**两条**链路

| | 作业 / 考试 | 课程任务点 |
|---|---|---|
| 粒度 | 一条条的待办 | 课程维度的进度指标（细化到小节） |
| 获取 | 两个列表页，**每次同步固定 2 个请求** | **必须逐课请求**（无全量接口） |
| 模型 | `TodoItem` | `ChaoxingCourse` |
| 界面 | 待办列表（「作业」视图等） | **独立的「课程」视图** |

不把任务点混进待办模型，是因为它没有截止时间、没有本地勾选、不参与「新作业」判定；
混进去会污染 `TodoItemViewModel` 的派生逻辑（逾期/倒计时/我的一天），
而且一门课动辄几十个小节（实测某课 40 个），拆成逐条待办会把列表淹掉。

## 二、分层骨架

每个来源一套「四件套」，命名与职责刻意统一：

```
XxxApiClient      传输 + 解析（该来源唯一的网络出入口）
XxxLoginService   WebView 登录与会话捕获
XxxSessionStore   登录态持久化（Windows 用 DPAPI 加密信封）
XxxSyncService    解析结果 → 领域模型映射
```

| 来源 | ApiClient | LoginService | SessionStore | SyncService | 会话文件 |
|---|---|---|---|---|---|
| 雨课堂 | `YktApiClient` | `YktLoginService` | `SessionStore` | `SyncService` | `session.json` |
| 学习通 | `ChaoxingApiClient` | `ChaoxingLoginService` | `ChaoxingSessionStore` | `ChaoxingSyncService` | `chaoxing-session.json` |
| 批改网 | `PigaiApiClient` | `PigaiLoginService` | `PigaiSessionStore` | `PigaiSyncService` | `pigai-session.json` |

三个会话文件都是 **DPAPI 加密信封**（`{"protected":true,"data":"<base64>"}`），
只保存会话 Cookie，**不保存账号密码**。

## 三、同步编排（一次同步的完整流程）

入口有两处，**走的步骤完全一致**：

- 手动同步：`RefreshAsync`（UI 线程，`[RelayCommand]`）
- 自动同步：`SyncForAutoAsync`（后台循环调用，结果再派发回 UI）

```
1. 网络与解析全部下到后台线程（Task.Run）
   └─ 雨课堂：SyncService.SyncAsync(_cacheFile, progress, ct)
              —— 唯一吃增量缓存的来源
2. 学习通链路A：SyncChaoxingAsync(warnings, cxSyncedAt, ct)
      └─ ChaoxingSyncService.SyncAsync → (Items, ForCache)
3. 学习通链路B：同一方法内 ChaoxingSyncService.SyncCoursesAsync
      └─ 课程列表 + 逐课任务点 → Courses
4. 批改网：SyncPigaiAsync(warnings, ct)
5. MergeExtraSources(雨课堂结果, 学习通条目, 学习通课程, 批改网条目, 警告)
6. ApplySyncResult(result, localState)   ← 必须在 UI 线程
      ├─ 落盘 todos.json
      ├─ BuildCache → _cache（待办）
      ├─ List.ReplaceCourses（课程）
      ├─ ApplyFilter / RefreshNavState
      └─ Synced 事件 → 桌面小组件刷新
7. AutoSync.Observe(result) → 差集判定「新作业」→ 通知
```

### 三个必须守住的编排约束

1. **`MergeExtraSources` 只调用一次**。`SyncResult` 的各 `*ForCache` 字段在每次新建
   对象时被整体赋值，分两次合并会让先合并那一路的缓存字段丢掉。
2. **`ApplySyncResult` 必须在 UI 线程**。它清空/填充 `ObservableCollection` 并触发
   `Synced`；自动同步跑在线程池上，必须显式 `Dispatcher.UIThread.InvokeAsync`。
3. **启动时必须 `await` 三个会话的恢复**，再开始首次同步。否则
   `SyncChaoxingAsync` / `SyncPigaiAsync` 会因为 cookie 还是 null 而整个跳过——
   表现为「冷启动后某个来源的作业不见了」。

### 容错约定

- **单源失败只降级**：每个 `SyncXxxAsync` 各自 `catch`，原因写进 `warnings`，
  界面顶部汇总成警告条，不中断其他来源。
- **登录态失效单独识别**：各来源有独立的 `XxxAuthExpiredException`，
  捕获后清空该源 cookie、置状态文字提示重新登录，**不影响另外两个来源**。
- **未登录直接返回空**（不报错）：`if (_xxxCookie is null) return …`
- **单课/单条失败只跳过该项**：雨课堂单课程失败继续下一门；学习通单课任务点
  读取失败只跳过该课；批改网整体失败降级为警告。

## 四、雨课堂：唯一按课程扇出、唯一有增量

**数据形态**：JSON 接口，多点位，**三源合并**。

| 步骤 | 端点 | 拿到什么 |
|---|---|---|
| 1 | `GET /v2/api/web/courses/list?identity=2` | 课程列表（按学期过滤） |
| 1b | `GET /v2/api/web/classroom_archive` | 已归档班级（不在课程列表，但内容接口仍可用） |
| 2 | `GET /v2/api/web/logs/learn/{cid}` | 学习日志 —— **作业与公告都从这里发现**（type 5/19/9） |
| 3 | `GET /mooc-api/v1/lms/learn/course/chapter` | 章节树：补试卷类截止时间、归一 leaf_id |
| 4 | `POST pub_new_pro` | `leaf_schedules` —— **完成状态的唯一权威来源** |
| 5 | `GET leaf_info/{cid}/{leafId}/` | 发布时间（拿不到退回日志时间） |

**核心机制**

- **完成状态不靠「截止时间过了没有」猜**，一律取 `leaf_schedules`；
  接口未返回该 leaf 时报「未知」而不是猜。
- **三源对齐靠标题归一化**：`leaf_schedules` 的键与 `/leaf_info/{room}/{id}/` 的 `{id}`
  都是**章节项的 `id`**，不是 `leafinfo_id`（后者查会返回 `Objects does not exist.`）。
- **增量捷径**（请求数大头是章节树 + 逐条详情）：每课按日志签名
  （id/类型/标题/发布时间/leaf_id/截止时间）SHA256 比对；签名未变 + 缓存里有该课作业
  + 距上次全量未超 **24h** → 只拉一次进度校验，跳过章节树与逐条详情。
- **24h 强制全量**兜住「日志不动」的变更（老师改截止时间、删章节项）。
  时间戳按课堂持久化，且**只在全量路径刷新**。
- **缓存存去重合并前**的列表（合并会丢课堂归属，被并掉的课下次无法走增量）。
- 单账号串行 `SemaphoreSlim` + 每请求 200ms 延迟（避风控）。
- 链接直达：试卷类用 `courseware_id`，章节作业用 `leaf_type_id` + `sku_id`，缺字段回落课程页。

**交付**：`HomeworkForCache`、`Announcements`、`CourseSignatures`、`CourseFullSyncedAt`

## 五、学习通：两条链路都吃 HTML

**数据形态**：服务端渲染的 HTML，**正则解析**（新版移动端 JSON 接口普遍要求 `enc`
令牌，纯 cookie 直调返回 `enc校验失败`）。

### 链路 A：作业 + 考试（两个固定请求）

| 列表 | 端点 | 解析依据 |
|---|---|---|
| 作业 | `GET mooc1-api.chaoxing.com/work/stu-work` | `<li data="…/mtaskmsgspecial…">` 块内 `aria-label="作业名称{}作业状态{}所属课程{}(剩余时间{})?"` |
| 考试 | `GET …/exam-ans/exam/phone/examcode` | `<li data="…/task-exam?…">` + `aria-label='考试名称：{}; 考试状态：{}; 剩余时间：{}'` |

**状态映射**（实测值）：

| 页面状态 | 映射 |
|---|---|
| `未提交` / `未交` | 未开始 |
| `待批阅` | 进行中（学生侧动作已完成） |
| `已批阅` / `已完成` / `已结束` | 已完成 |

**相对时间的处理（关键）**：页面只给「剩余 X 天 X 小时 X 分钟」，绝对时间是用
**同步时刻**推算的。因此缓存**存「基准 + 相对量」而不是只存推算出的绝对值**：

```
TodoItem.DeadlineAnchor  = 基准时刻
TodoItem.RemainingAtSync = 当时的相对剩余量
EffectiveDueAt           = DeadlineAnchor + RemainingAtSync
```

只存绝对值的话，应用关三天再打开，缓存首屏会显示「剩余 2 天」而实际只剩几小时。
旧缓存没有基准字段的，加载时用缓存自身的 `SyncedAt` 回填。

### 链路 B：课程未完成任务点（逐课请求）

| 步骤 | 端点 | 说明 |
|---|---|---|
| 1 | `GET mooc1-api.chaoxing.com/mycourse/backclazzdata?view=json&rss=1` | 一次拿到 **clazzId**（`content.id`）/ **courseId**（`course.data[0].id`）/ **personId**（`content.cpi`）/ 课程名 / 班级名 / 是否结课 |
| 2 | `GET mooc1-2.chaoxing.com/visit/stucoursemiddle?courseid=&clazzid=&vc=1&cpi=` | 课程首页，**不需要 `enc`**；含「待完成任务点」章节树 |

**解析口径（两个坑）**

1. **只统计叶子章节**。父层级的 `knowledgeJobCount` 是子层级的**汇总值**，
   朴素求和会重复计数（实测某课 16 vs 13）。
   判定：某个带任务点的章节，若它之后还存在更深层级的任务点，它就是汇总，跳过。
2. **必须先按文档位置排序**。标记是按层级
   （`levelfirst`→`leveltwo`→`levelthree`）收集的，不是文档顺序；
   而叶子判定靠位置先后。不排序会漏掉「父在前、子在后」这种最常见情形。

同一个解析同时兼容两种课程结构：有的课没有三级嵌套（任务点全在 `leveltwo`），
有的课有 `levelthree`。**没有「待完成任务点」区块 = 该课没有未完成项**（得 0，不是错误）。

**不做预过滤**：曾经按 `isretire == 1` 跳过查询以省请求，结果漏掉了
`信号与系统`（13 个未完成任务点）——它在响应里根本没有 `isretire` 字段。
现在一律请求。

**交付**：`ChaoxingForCache`（待办形态）、`ChaoxingCourses`（课程维度汇总）

## 六、批改网：单列表，难在登录

**数据形态**：服务端渲染的 HTML，**正则解析**。

| 项 | 内容 |
|---|---|
| 列表 | `GET www.pigai.org/index.php?c=write&a=waitComplete&bf=4`（`bf=4` = 「作文」类型） |
| 登录 | `POST /index.php?a=login`（`username` / `password` / `remember`） |
| 结构 | 表头 `<ul class="reItemM">`，每条一个 `<ul class="reItemS">` |
| 列 | 作业号 / 标题 / 类型 / 出题人 / 指定班级 / 截止时间 / 操作 |

**登录捕获（严格照搬雨课堂那条已跑通的路径）**

- **async 轮询循环**（`Task.Delay` + `ConfigureAwait(true)` 回到 UI 线程），
  **不是** `DispatcherTimer`——`NativeWebView` 是 COM/STA 控件，续体切到线程池会让
  `InvokeScript` 永不返回。
- **页面内探测脚本必须同步返回**：WebView2 不等待 Promise，会把等待中的 Promise
  序列化成 `{}`。脚本只负责发起 fetch 并把结果写进 `window.__hrPigaiLogin`，
  本次读出上一次的结果。
- **判定看响应正文而非状态码**：批改网未登录时受限页面**照常返回 200**，
  只是渲染「使用此功能，请先登录」。
- **登录是否成立由探测结果判定，不由 cookie 名判定**。曾经要求 cookie 里必须有
  `_JKU`，而真机登录后未必有该项 → 探测说已登录、代码却一路跳过，
  **会话永不落盘**，表现为「登录过、重启仍显示未登录、待办里没有作文」且完全静默。
  现在只要读到 pigai 域 cookie 就保存。
- 每次探测外包 **3 秒超时**，避免页面跳转中途把循环拖住。

**映射**：状态统一「未开始」（未完成列表本身就是待办语义）；
主标题用**出题人**、副标题用作文标题；截止时间是列表里的绝对时间串。

**交付**：`PigaiForCache`

## 七、四个模型与稳定 Id

| 模型 | 用途 | 备注 |

| `TodoItem` | 待办条目（作业 / 考试 / 公告） | 三源共用 |

## 八、持久化与冷启动

`todos.json`（`TodoCacheFile`）五个字段，与三条链路一一对应：

| 字段 | 来源 |
|---|---|
| `Homework` | 雨课堂（去重合并**前**的列表） |
| `Chaoxing` | 学习通作业/考试（保留基准 + 相对量） |
| `Pigai` | 批改网 |
| `ChaoxingCourses` | 学习通课程任务点汇总 |
| `Announcements` | 雨课堂公告 |
| `CourseSignatures` / `CourseFullSyncedAt` | 雨课堂增量同步的比对基准 |

加载时逐类**合法性校验**，丢弃坏条目（缺 id/标题、id 前缀与类型不符、
时间戳离谱、重复 id、缺课程名的课程）——缓存文件可能被手改或被旧版本写坏。

**冷启动顺序**：

```
读 local-state.json
读 todos.json ──→ BuildCache + ReplaceCourses + ApplyFilter（首屏秒开）
读 session.json / chaoxing-session.json / pigai-session.json（三个都 await）
逐源同步（网络追平）
```

## 九、界面消费

| 视图（`SelectedNav.Key`） | 数据来源 |
|---|---|
| 我的一天 / 计划内 / 作业 / 公告 / 已完成 / 全部 | `_cache`（待办），按时间与状态过滤 |
| **课程** | `List.Courses`（课程汇总），**另一条通道** |

两条通道由 `List.ShowCourseList` 切换，空状态文案由 `List.HasAnyContent` 统一决定
（`ShowCourseList ? Courses.Count > 0 : VisibleItems.Count > 0`）。

- 倒计时与逾期标红由**独立的分钟级计时器**刷新（`RefreshTimeDependentState`），
  **不依赖同步成功**——关掉自动同步或长时间离线时，时间仍照常走；跨天会重算「我的一天」。
- 角度说明：**待办**导航的角标是「未完成待办数」；**课程**导航的角标是
  「有未完成任务点的课程数」（不是任务点总数——那是每门课的明细）。
- 桌面小组件复用 `_cache`（`WidgetSource`），不额外请求网络。

## 附：三条踩过的坑（都值得保留）

1. **不要用「某个 cookie 名存在」去否决已经确认的登录**——判定权归探测 / 接口。
2. **相对时间不能只存推算出的绝对值**，要存基准 + 相对量。
3. **WebView 登录捕获要主动轮询**，不能只等导航事件；必须在 UI 线程，
   探测脚本必须同步返回。
4. **不要用「看起来能省请求」的字段做预过滤**（如 `isretire`）——
   字段缺失时会把正常课程一起跳过，而且是静默漏报。
5. **解析嵌套结构时先按文档位置排序**再做「是否有更深层子节点」这类判定，
   按类型分轮收集得到的顺序不是文档顺序。
